## Problem Statement

The Karibu webapp was built as the original MVP/proof-of-concept before the Android
app existed, and was shaped mobile-first because clinics only had phones on cellular.
Two things changed underneath that decision:

1. The Android app now owns mobile clinical entry, pharmacy, and lab better than the
   webapp ever could (offline-first via Room + WorkManager + SyncEngine, role-based
   homes). The webapp is wearing a costume sized for a job it no longer holds.
2. Repeatable wifi installation in clinics is now solved, which puts *screens* in the
   room — laptops and tablets — for the first time. That is a new surface the webapp
   was never designed for.

The opportunity: stop making the webapp a worse phone, and make it the thing a phone
cannot be — the desk/station surface that holds breadth and depth a 6-inch screen
physically can't. Reimagine the laptop information architecture rather than piecemeal-
patching the mobile layout into one.

Important nuance discovered during codebase mapping: the webapp shell is already
desktop-oriented (fixed 232px sidebar, `max-w-7xl`, tables that stack defensively on
mobile). The "POC flavor" is not a phone layout. It is (a) shallow layout grammar —
detail opens as a cramped right-side `Sheet` (`PatientDetailClient.tsx:11`,
`!w-full sm:!max-w-md md:!max-w-lg`) instead of true master-detail, and queues are
vertical card lists instead of landscape tables — and (b) a navigation model with no
concept of scope or role-as-place, patched by a bolted-on "admin cross-area switcher"
(`web-shell.tsx:41-46,120-126`, commit d5358d9).

## Demand Evidence

Founder is the primary evidence source today (uses it on a laptop himself, knows where
it feels POC-ish). The founder is remote (different country from the users), so direct
observation is not available. Feedback arrives two ways: PostHog for some instrumented
signals, and — for most of it — by shipping a near-complete fix and collecting user
reactions via text/email. Three desk personas are specified with real workflows and
volumes, but have not yet been validated against real users on a laptop:

- **Local administrator** — a seasoned pro running 2 clinics. Needs MoH/HMIS data for
  submission and to "run payments well." Framed explicitly as **P&L plus public health.**
- **Diocese level (near-future requirement)** — in Uganda clinics are run by Catholic
  and Anglican dioceses; one diocese runs **20+ clinics.** Needs oversight across all
  Karibu clinics in the diocese, alongside the local admin who only cares about her own.
- **Pharmacy and lab** — stationary roles, same room all day, legitimately better with a
  landscape queue than vertical scroll. Volume: **40-50 patients/day, ~2 tests each,
  malaria-heavy.**
- **Clinician** — initial pass on the phone (most visits complete there); moves to
  desktop for inpatient or complicated cases. The laptop clinician view is the
  deep-work / review-and-sign view, not a re-do of the phone form.

## Status Quo

- Clinical entry, vitals, dictation, pharmacy dispense, lab results: done well on
  Android, offline-first.
- Desk/depth work today is cramped onto a phone-shaped webapp or done on paper/Excel and
  re-keyed (HMIS, payments).
- The webapp already has role homes (clinician/pharmacy/lab/analyst sidebars via
  `roleForPath()`, role-gated redirects in `dashboard/page.tsx:56-81`) but the layout
  grammar underneath is POC-level.

## Target User & Narrowest Wedge

**Narrowest wedge to ship first: one station role's landscape workspace** (pharmacy or
lab). It is the most self-contained (queue + capture, no deep chart), the volume makes
the landscape win obvious (40-50 × 2 tests), and it proves the master-detail layout
primitive before the harder surfaces (diocese rollup, P&L) are built. Ship it, watch a
real dispenser/lab tech use it for a day, then expand the same grammar outward.

## Constraints

- **Tier-graceful is non-negotiable.** Tier 1 = clinician Android on cellular only, must
  fully work. Tier 2 = wifi + laptops/tablets/phones, should work fluidly with clean
  device-to-device handoffs. The laptop webapp is additive; it never strands cellular-only
  clinics.
- **Reuse much of it.** This is a shell/IA reimagining over mostly-intact clinical logic,
  not a teardown. Same Supabase/Clerk/server-actions stack, same dashboard routes and data.
- **Keep Clerk where it is strong** — identity, sign-in, password self-service, org =
  clinic. Do not flip Clerk org to diocese.
- Coherent design system already exists (Karibu tokens in `globals.css:11-73`, shadcn
  foundation). Extend, don't replace.

## Premises

1. The webapp's job is changing from "mobile clinical entry" to "the desk/station
   surface." Android stays primary mobile/field. — AGREED
2. The problem is information architecture and layout grammar (real master-detail,
   landscape density, a real scope model), not responsive CSS and not mobile-vs-desktop.
   — AGREED (refined: shell is already desktop; the gap is depth/density + scope)
3. Three+ desk personas drive the design and are different products sharing a shell:
   pharmacy/lab stations, clinician deep-work, local admin (P&L + HMIS), and **diocese
   cross-clinic oversight as a first-class scope, not an edge case.** — AGREED (the
   diocese tier is the most important correction in the session)
4. Tier-graceful across hardware setups. — AGREED
5. Shell/IA reimagining, not a rewrite; reuse much of the existing dashboard and all of
   the backend. — AGREED (leans reuse)

## Approaches Considered

### Approach A: Role homes + laptop layout kit (minimal viable)
Keep all routes; add a laptop-first AppShell with a multi-pane primitive and dense
landscape tables; tune each role landing; bolt diocese on as a new scope switcher +
one rollup dashboard. Lowest risk, fastest, but risks re-accreting holdover navigation
and treating diocese as an afterthought.

### Approach B: Scope + Workspace grammar (ideal architecture) — CHOSEN
Reconceive around two axes:
- **Scope** (diocese → clinic): a persistent switcher. For a clinic user the switcher is
  the Clerk org switcher (clinic). For a diocese user there is a diocese scope one level
  above, backed by oversight-plane RPCs. The auth hierarchy and the UI scope axis are the
  **same construct.**
- **Workspace**: one master-detail layout grammar (list pane + detail pane) that every
  role instantiates differently — pharmacy = queue + dispense; lab = queue + result entry;
  clinician = worklist/visits + chart; local admin = registers/reports + detail; diocese =
  clinic-list + clinic-detail rollup.

One layout language, four+ expressions. Diocese falls out as "the top scope" instead of a
special case. Kills the cross-area-switcher patch at the root.

### Approach C: Station mode vs Console mode (lateral)
Two distinct experiences: a kiosk-like single-purpose Station (pharmacy/lab/registration,
fullscreen landscape queue, minimal chrome) and a multi-pane analytical Console (clinician,
admin, diocese). Best per-persona fit, but two shells to maintain for a small team.
Absorbed into B: "Station" becomes one expression of B's grammar (a workspace that hides
the scope rail and maximizes the queue), not a second shell.

## Recommended Approach

**Approach B, sequenced so the first shippable slice is one station role**, getting
A's ship-fast-and-validate rhythm inside B's architecture. C's Station idea survives as a
workspace mode within B.

### Why B is correct given the codebase
- Role homes, role gating, and coherent design tokens already exist — B extends them.
- The "admin cross-area switcher" (d5358d9) is a symptom of a missing scope model; B
  supplies the model and retires the patch.
- Detail views are cramped `Sheet` panels today; B's master-detail primitive is the
  direct fix and is reused by every persona.
- The diocese tier maps cleanly onto B's scope axis AND onto the auth model (below), so
  it is designed once and serves both security and navigation.

### Auth / scope architecture (the load-bearing decision)
Confirmed against migrations. Do NOT flip Clerk org from clinic to diocese (≈20 RLS
policy rewrites, webhook rewrite, breaks `get_current_clinic_id()`, 3-4 weeks, data-leak
risk). Instead, three planes:

- **Operational plane (Clerk-native).** Active Clerk org = clinic (keep
  `clinics.clerk_organization_id`, `get_current_clinic_id()` from `auth.jwt()->>'org_id'`,
  migration 006). Clerk's org switcher doubles as the clinic switcher for multi-clinic staff.
- **Role plane (Supabase-native).** `staff.role` is the real functional role, per clinic.
  Clerk org role stays coarse (member/admin). Supabase is source of truth (webhook
  `resolveStaffRole()` already honors `staff_invitations.role`).
- **Oversight plane (Supabase-native).** Promote diocese from a TEXT tag
  (`clinics.diocese`, migration 025) to a first-class entity: a `dioceses` table,
  `clinics.diocese_id` FK, and generalize `diocese_coordinators` (migration 052) into
  `diocese_members(clerk_user_id, diocese_id, role)`. Diocese rollup reads run through
  SECURITY DEFINER RPCs that check `is_diocese_member(diocese_id)` and aggregate across
  all clinics in the diocese — the exact pattern outbreaks already proved.

**DECIDED in eng review (decision 1A): keep operational RLS scalar, make identity
org-aware.** The 94 `clinic_id = get_current_clinic_id()` references across 20 migrations
stay UNTOUCHED. `get_current_clinic_id()` (006:21-50) already resolves the active clinic
from `auth.jwt()->>'org_id'`, so a multi-clinic user is correctly scoped to whichever
clinic's Clerk org is active. Set-membership (`clinic_id IN (...)`) was rejected: it would
bleed Clinic B's patients into Clinic A's operational views and regress query plans.
Multi-clinic = "belong to multiple Clerk orgs, switch the active one."

The real, smaller work:
- Relax `staff.clerk_user_id UNIQUE` (001:23) → composite `UNIQUE (clerk_user_id,
  clinic_id)` (or a `staff_clinic_roles` junction). One user, one row per clinic.
- Make **staff-identity resolution org-aware** (the actual landmine): `get_current_staff_id()`
  (006:53, referenced 49×) and the 25 inline `staff WHERE clerk_user_id = sub LIMIT 1`
  sites currently pick an ARBITRARY staff row for a multi-clinic user — wrong for
  authorship/audit. Redefine `get_current_staff_id()` to resolve the staff row for the
  ACTIVE clinic (via `org_id`); migrate the 25 inline sites to call it (DRY).
- Make web `getStaff()` org-aware: use Clerk `auth().orgId` to select the `(user, active
  clinic)` staff row instead of `.single()` on user (which throws once a second row exists).
- Update the Clerk webhook to upsert on `(clerk_user_id, clinic_id)`.

Cross-clinic DIOCESE reads do NOT go through base-table RLS — they go through separate
SECURITY DEFINER RPCs that check `is_diocese_member()` and select
`clinic_id IN (clinics WHERE diocese_id = X)`. New code, not a rewrite of the 94.

**Remaining flag for /plan-eng-review:** diocese rollup over HMIS 105 (heavy multi-table
report, migrations 013/014) across 20+ clinics is very unlikely to be feasible on-demand.
Plan to materialize/precompute diocese aggregates; treat live computation as the exception.

**DECIDED (decision 2A, revised after outside-voice challenge) — defer ALL auth/JWT/
middleware work.** There is ONE clinic in production today. The near-term build touches
NO auth, DB, RLS, or middleware code. It is frontend-only.

Why the revision: the original 2A would have shipped `org_id`-in-JWT + active-org
middleware "now" as a cheap foundation. Verified that this is the opposite of cheap:
- Web server actions use the service-role client (`supabase.ts:20`), which BYPASSES RLS.
  So `get_current_clinic_id()`/`org_id` RLS is not exercised by web at all.
- The org_id RLS path is exercised only by Android's authed JWT, which uses the DEFAULT
  Clerk session token (`ClerkAuthManager.kt:115-118`). Whether it carries `org_id` and
  whether an active org is set is unverified external Clerk config.
- Making RLS depend on `org_id` for the first time risks fail-closed lockout (every query
  returns empty, not just login) for a single clinic that gains nothing from it.

So all of the following is deferred to real triggers, NOT this PR:
- **When clinic #2 lands:** add `org_id` to the JWT + active-org middleware AND treat it as
  a load-bearing auth change tested at the data-access level (not just login); relax
  `staff.clerk_user_id UNIQUE`; make `get_current_staff_id()` + the 25 inline lookups
  org-aware; fail-close the `get_current_clinic_id()` fallback. NOTE a live latent bug to
  fix here: `upsertStaff` already keys on `(clerk_user_id, clinic_id)` (`clerk.ts:331-332,
  358-359`) but `staff.clerk_user_id` is still UNIQUE (001:23) — the first cross-clinic
  user will throw a unique violation in the webhook until the constraint is relaxed.
- **When the diocese arrives:** promote `clinics.diocese` TEXT → `dioceses` + `diocese_id`
  FK; generalize `diocese_coordinators` → `diocese_members`; materialized rollup RPCs.

The near-term product work (layout primitive + one station-role landscape workspace) ships
against the single pilot clinic immediately, against existing auth, with no backend change.

### Division of labor with Android (the ecosystem)
- **Android = resilient field surface:** dictation/notes, vitals, registration, lab/pharmacy
  role homes (offline dispense + local stock decrement, offline lab results), patient chart
  with status pills, "Send to pharmacy."
- **Web = desk/ops/admin/AI surface:** AI review queue + sign/cosign/amend/void (audit),
  stock reconciliation + catalog admin, HMIS reporting + data quality, billing worklists,
  outbreak/protocol management, superadmin provisioning, and the new diocese rollup.
- **Handoff seam (already structurally present):** visit lifecycle pending → review → sent
  → completed (`packages/shared/src/types.ts`). Clinician drafts + orders on phone (note
  stays `pending`, pharmacy queues on `pharmacy_order_submitted_at`), then signs after AI
  review on the laptop. The phone-to-desktop escalation the founder described maps exactly
  onto this; B should make "continue this visit on the laptop" a first-class moment.

## Relationship to ADR-0001 (per-subdomain split)

Checked against `docs/architecture/adr-0001-per-subdomain-apps.md` (status: Proposed,
phased, no big-bang) and the actual repo. The split is NOT yet implemented (`apps/` =
android, learn-android, web). Resolution for this redesign:

- **The EHR is not split.** `apps/web` stays one app (Clerk, per-clinic, existing RLS),
  only its deploy domain moves to `ehr.karibu.health`. The diocese oversight surface is
  clinical / Clerk / PHI (drills down to identifiable clinics), so it correctly lives in
  this EHR app — not in the investor or apex apps. This redesign proceeds inside `apps/web`
  independent of the split timeline.
- **Scope `/learn` and `/library` OUT of this redesign.** ADR sequencing step 2 lifts
  `apps/web/src/app/learn/**` (and library) into a new `apps/learn-web` with Supabase Auth
  and no Clerk. Do not invest laptop-IA work in those routes — they are leaving. The
  Scope+Workspace grammar applies to the clinical/admin/diocese dashboard only.
- **One aggregation layer, two consumers.** The materialized diocese aggregates this design
  needs (HMIS/P&L rolled up across 20+ clinics) are the same architectural shape as the
  investor portal's "impact metrics" layer (ADR lines 134-145: aggregate, de-identified
  rollups the EHR publishes into). Design the diocese rollup mechanism (scheduled rollup
  tables / metrics RPCs) so it can also feed the future investor metrics layer, with
  different read-scoping: diocese member sees their diocese's identifiable clinics; the
  investor app reads only global de-identified aggregates and never touches EHR tables
  directly. Build cross-clinic aggregation once.

## Open Questions

- Is multi-clinic for ordinary clinical staff a now-requirement, or is the near-term
  multi-clinic need only the local admin (2 clinics) + diocese oversight? This sets how
  urgently the `staff.clerk_user_id` relax must ship vs. being architected-for.
- **Diocese-only users with no operational clinic.** A pure diocese overseer may have no
  clinic Clerk org at all, which breaks the "active org = clinic" assumption for their
  session. Does the diocese scope need its own auth context (e.g. a diocese Clerk org, or
  a diocese-scoped session that bypasses `get_current_clinic_id()` entirely)?
- **Audit on cross-clinic reads.** A diocese member aggregating 20 clinics' PHI/HMIS is a
  privacy-relevant access path. Diocese rollup RPCs must emit audit entries via the
  existing `_shared/audit.ts` infrastructure — confirm the audit schema covers diocese-scope
  reads, not just clinic-scope writes.
- Diocese rollup reads: precompute/materialize aggregates (20+ clinics × HMIS) or compute
  on demand? Performance + freshness tradeoff for /plan-eng-review.
- Tablet: is it a Tier-2 web client (responsive Console) or an Android client? Affects how
  far down the breakpoint ladder the laptop grammar must remain usable.
- P&L is greenfield (Reports lists Profitability as "coming soon"). Is a real P&L surface
  in scope for this effort, or does the admin workspace ship with HMIS first and P&L later?

## Success Criteria

Validation is remote: PostHog instrumentation plus shipped-fix-then-text/email feedback,
not in-person observation. Criteria are written to be measurable that way.

- A dispenser or lab tech runs a full 40-50 patient day on the laptop landscape workspace.
  Measured via PostHog (laptop sessions for that role, time-on-workspace, queue actions
  per session) and a direct text/email ask after a week of use ("phone or laptop for your
  queue now, and why").
- The admin cross-area switcher (d5358d9) is removed because scope/role navigation makes it

- Tier 1 (Android on cellular) is unchanged and fully functional throughout (regression

## Station workspace UX spec (NOW lane — build contract)

Design review complete (2026-06-16). This section is the implementable UI contract for
agents building steps 1–3. Calibrate against Karibu tokens (`globals.css:11-73`) and
existing queue tables (`PharmacyQueueClient.tsx`, `LabQueueClient.tsx`). No `DESIGN.md`;
extend tokens, do not introduce new palette.

### Component vocabulary

| Component | Responsibility |
|-----------|----------------|
| `MasterDetail` | Shared two-pane primitive (`react-resizable-panels`). List slot + detail slot. Handles collapse, keyboard shell, pane min widths. |
| `StationWorkspace` | Pharmacy or lab page composition: `WebTopBar` + `MasterDetail` + queue table + detail panel. |
| `QueueTable` | Landscape dense table (not card-wrapped). Header row + selectable rows. |
| `WorkspaceTopBar` | Extends `WebTopBar`: role label, queue count, oldest-wait anchor, secondary actions (History). |

Export `STATION_COLLAPSE_BP = 1024` from `MasterDetail` (shared with tests). Below this
width, two-pane collapses to list-only + detail as sheet/drawer (not full-page overlay).

### Chrome budget (v1 pilot — single clinic)

- **Scope rail:** hidden in NOW lane (no diocese, one clinic). Do not build a placeholder
  rail; clinic name stays in existing sidebar header (`web-shell.tsx:132-137`).
- **Sidebar:** keep 232px role sidebar as-is for v1. Do not add a second navigation
  metaphor inside the workspace.
- **Admin cross-area switcher:** keep until scope rail ships (clinic #2 / diocese). Removal
  is a success criterion for a later phase, not this PR.
- **Minimum viewport:** 1280×720. At 1366×768, list + detail must both be usable without
  horizontal scroll on the queue columns defined below.

### Layout (pharmacy station v1)

```
┌──────────┬──────────────────────────────────────────────────────────────┐
│ Sidebar  │ WorkspaceTopBar: Today · PHARMACY · {n} awaiting · oldest {t}│
│ (232px)  ├─────────────────────────────┬────────────────────────────────┤
│          │ List pane (~40%, min 320px) │ Detail pane (~60%, min 360px)  │
│          │ QueueTable                  │ Patient context + full dispense│
│          │ · row select highlight      │ · Dispense + stock dialog here │
│          │ · quick actions INLINE      │ · notes, med list, history link│
│          │   (Quick mark, Partial, Out)│                                │
└──────────┴─────────────────────────────┴────────────────────────────────┘
```

Lab station: same shell; detail pane = result entry + test list instead of dispense.

Default pane split: 40% list / 60% detail. User-resizable via drag handle; persist split
ratio in `sessionStorage` key `kh-station-split` (optional v1 — default fixed split OK if
resize works within session).

**Do not** wrap the queue in an outer `rounded-xl` card. Use flat surface: page background
+ row dividers (`border-line-soft`), matching existing column headers.

### Hybrid action model (throughput-critical)

Pharmacy/lab serve 40–50 patients/day. **Do not** require opening the detail pane for the
common path.

| Action | Location | Rationale |
|--------|----------|-----------|
| Quick mark dispensed | List row (inline button) | One click; preserves today's workflow |
| Partial / Out of stock | List row (inline button) | Same |
| Dispense + stock (dialog) | Detail pane primary CTA **or** list row button that opens dialog scoped to row | Full stock movements need space |
| Notes (multi-line) | Detail pane | Too cramped inline at scale |
| Patient chart link | Detail pane header | Deep context |

**Rule:** list row keeps at least Quick mark + Partial + Out without selecting detail.
Selecting a row loads detail for context and full dispense; it must not block quick actions
on other rows.

### Selection model

- On load with queue items: auto-select first row (oldest first, existing sort).
- Selected row: `bg-cobalt-soft` background + 3px left border `border-l-cobalt` (use tokens,
  not generic blue).
- Click row → select + load detail. Click another row → switch selection.
- **After successful dispense:** remove row from queue (existing revalidation), auto-select
